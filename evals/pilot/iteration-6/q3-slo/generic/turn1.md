先说结论：「所有服务 P99 < 100ms」不能直接当验收目标，只能当「用户要同步等待的那几个接口」的目标。常见的性能改造清单默认了两件事：瓶颈已知，且所有接口同一目标——这里两件都不成立。照字面做，大部分预算会花在没人等的批处理和异步任务上；不先测出 P99 花在哪，清单里的优化顺序也一定是错的。

**先把范围砍到能定义的程度**

- 只有用户点击后同步等结果的接口值得谈 100ms（详情、搜索、下单、支付前校验）。定时任务、消息消费、报表、内部同步没有「用户等待」，给它们定 100ms 只会逼出无意义的并行和缓存。
- 100ms 是端到端（含网关、鉴权、DB、下游）还是单服务自身？若是端到端，单服务预算往往只剩 20–30ms，做法完全不同。
- 这几个接口现在的 P99 是多少？120ms 和 1.5s 是两个项目：前者是长尾治理，后者是砍依赖链。
- 一次请求串行经过几次 DB/RPC、有没有第三方？第三方 P99 本身超过 100ms 的，目标只能改成异步或降级，否则无解。

**清单（按对 P99 的杠杆排序；先做第 0 步，再定从哪条开始）**

0. 测量：按接口出自己的 P50/P90/P99/P999，把一次请求拆成 自身计算 / 依赖调用 / 排队等待 三段；客户端与网关耗时单列。低频接口样本不够时 P99 就是噪声，用一周滚动窗口，别拿一次压测下结论。

1. 砍串行依赖：独立的下游调用并发发；去掉循环里的单条查询（N+1）；能一次批量取的不逐个取。每多一跳就多一份尾延迟叠加，这一项通常收益最大。

2. 治排队：连接池/线程池按峰值并发配，把「取连接等待时间」单独打点；关键接口用独立池，与批处理隔离；下游设超时 + 最多一次带退避的重试，禁止无限重试——重试风暴是 P99 最常见的自造来源。

3. 减少请求路径上的工作：热读加本地 + 分布式缓存（想清楚一致性与击穿）；日志、通知、推荐、审计移到异步；能离线预计算的就预计算，在线只读一次 KV。

4. 处理运行时抖动：看 GC 停顿是否正好落在 P99 时段，再决定换低停顿收集器还是减分配；冷启动用预热，发布后先预热再放量；确认没有实例在 swap 或被邻居抢 CPU。

5. 数据层只在有证据时动：慢查询日志指向哪条 SQL，就做索引、限量、分页或读写分离，不要凭感觉给全表加索引。

6. 明确不做：不给异步和批处理套 100ms；P99 坏但 CPU 不高时先别扩机器（问题在排队不在算力）；不要所有接口一起改，先拿一个接口走完 0–3 步，量出收益再复制。

**怎么算做到了**

纳入范围的接口，连续 7 天同一统计窗口 P99 ≤ 100ms，且 P99.9、错误率、超时率、降级率不上升；窗口里至少包含一次发布和一次流量峰值。反向信号：靠把超时压到小于依赖的 P99 来「达标」，错误率或降级率一涨就是假达标，应退回。

**需要你给的四个数**

哪几个接口算用户同步等待、它们现在的 P50/P99、单次请求的串行跳数与第三方依赖、100ms 是端到端还是单服务。给我这四个，我把上面的通用清单收敛成按接口排的改造顺序和预算。

对老板的说法建议改成：不是做不到，是「所有」会把预算摊薄；先对用户可感知的接口承诺 100ms，其余服务给各自合理的目标。
