# 结论先说

"所有服务 P99 都做到 100ms" 不能直接当施工图用。照着一刀切地改，大概率是花大钱把报表导出、对账批处理、异步通知这类本来就不该追延迟的服务硬拧到 100ms，而用户真正卡的地方没动。这个要求要先翻译成三件事：**哪些服务、什么口径的 P99、端到端预算怎么分**。清单我下面给，但这几条得先和老板对齐。

## 一、这个指标本身有几个坑

1. **粒度不对。** P99 是哪个端点的？服务级聚合会把 99% 的快请求和 1% 的慢接口搅成一个数，最后谁都不认账。必须按 endpoint/接口维度定。
2. **口径不清。** 服务端 P99 还是客户端可感知的 P99？中间还隔着网关、网络、重试、前端渲染。老板嘴里的"卡"多半是客户端那个数。
3. **扇出会放大。** 一个页面并行打 15 个服务，每个服务 P99 都是 100ms，那端到端至少一个慢的概率 ≈ 1−0.99¹⁵ ≈ 14%。所以 100ms 应该给端到端，再按预算往下拆，而不是每个服务抄同一个 100ms。
4. **有物理下限。** 同 AZ 的 RTT 约 0.3–1ms，跨 AZ 1–3ms，跨地域 30–200ms。同步写多副本、跨地域强一致、串行三跳外部依赖，这些场景 100ms P99 不是优化问题，是业务决策问题。
5. **低流量服务算不出有意义的 P99。** 一分钟几十个请求，P99 就是某一两个慢请求，波动全靠运气。得设样本量门槛。
6. **尾部延迟不线性。** 均值压一半容易，P99 每降一个量级，成本指数上升。要先问清楚"100ms 是硬指标还是表达'要快'的愿望"。

## 二、先做三件事（1–2 周，别跳过）

- **服务清单与分档。** 按用户是否同步等待分档：A 档是用户同步主链路（登录、下单、详情、支付回调），B 档是用户可感知但能异步/延后（通知、积分、搜索索引），C 档是后台批处理与内部任务（报表、对账、离线计算）。**只对 A 档承诺 100ms**，B 档给 300ms 量级，C 档追吞吐和完成时间。
- **统一口径和埋点。** 服务端、网关、客户端三层都要有 P99；窗口用 5 分钟和 1 小时两套；样本量不足的不出 P99，改看 P95 或直接标"数据不足"。同时打开全链路 trace，每个 span 记耗时。
- **建立基线，找 top 瓶颈。** 没有基线的优化都是猜。用生产 trace 加一轮压测，按"该接口贡献的超时请求数 × 超出幅度"排序，通常前 5 个接口吃掉 80% 的问题。

## 三、改造清单（按性价比从高到低）

### 0. 观测与门禁（先做，否则后面白做）

- 每个 endpoint 一张 SLO 看板：P99、错误率、超时率、吞吐。
- 客户端 RUM，采集真实用户 P99（这才是老板感知的数）。
- 慢查询日志、GC 日志、连接池/线程池水位、队列积压，全部进监控。
- 发布门禁：金丝雀发布 + 与基线对比 P99，劣化超过 10% 自动回滚。
- 告警用错误预算燃烧率（burn rate），不要用瞬时 P99 抖动，否则天天误报。

### 1. 调用链与扇出（收益最大、最便宜）

- 画出每个用户请求的扇出数和串行深度；能并行的改并行，能合并的合并。
- 非关键路径同步改异步：通知、审计、积分、搜索索引、推荐日志。
- 消灭 N+1：批量接口、请求合并（类似 DataLoader 的做法）、一次查多条。
- 超时与重试预算：每跳 timeout 必须小于剩余预算，禁止无上限重试；加熔断和降级。
- 预计算/物化：首页、榜单、聚合统计离线算好，线上只读。

### 2. 接入与网络

- 连接复用：keep-alive、连接池、HTTP/2 或 gRPC，TLS session resumption，证书 OCSP stapling。
- 就近接入：多 AZ 部署、GSLB/智能 DNS、静态资源走 CDN 和边缘缓存。
- 响应体治理：压缩、字段裁剪，大 JSON 是常见的 P99 杀手。
- 负载均衡健康检查与长连接配置，避免请求跨 AZ 无谓多跳。
- 过载保护：限流 + 排队 + 降级，靠丢弃保 P99，不靠硬扛。

### 3. 应用层

- 连接池/线程池按 Little's law 估算并压测校准，别用框架默认值；池满就是排队，排队就是 P99 爆。
- GC：换低延迟收集器，控制堆大小和分配速率，避免大对象和频繁扩容。
- 序列化：换更快的编解码，避免同一份数据反复序列化。
- 少做事：字段裁剪、懒加载、分页、结果缓存；同步日志改异步或采样。
- 冷启动：预热、常驻实例、依赖预取，避免扩容后第一批请求全慢。

### 4. 数据层（多数系统 P99 的最大头）

- 慢查询 top N 逐个处理：加索引、改写 SQL、去掉 `SELECT *`、避免函数包字段。
- 深翻页改游标分页；大结果集改流式或分片。
- 读写分离、只读副本；热点 key 拆分，避免单分片打满。
- 缓存：本地缓存 + Redis 两级；防击穿（单飞/互斥重建）、防雪崩（TTL 抖动）、防热点；一致性策略写清楚。
- 事务与锁：拆长事务，缩短行锁持有时间；死锁重试要有上限。
- 写路径：批量提交、异步落库（配幂等），重新评估是否真的需要同步多副本强一致。
- 连接数治理：DB 连接池上限 + 连接代理，避免应用扩容把数据库打爆。

### 5. 异步与削峰

- 队列解耦非关键路径，消费端批量拉取 + 并发度控制，避免消费积压反压。
- 写合并、去重、幂等键，防止重试风暴。
- 高峰期排队并把"慢"显式化成"稍后处理"，比让用户干等体验好。

### 6. 依赖与第三方

- 第三方 API 的 P99 必须纳入预算；本地缓存兜底，超时走降级值。
- 对不可控依赖设 deadline，禁止把用户请求挂在别人的长尾上。

### 7. 基础设施

- 容量按峰值 2 倍压测，弹性扩容要预热，别等打满才扩。
- 隔离 noisy neighbor：独立资源池、cgroup 限制、关键服务不与批任务混部。
- 检查磁盘 IO 和临时文件（日志、上传、缓存目录），IO 抖动经常表现为尾延迟。

## 四、怎么验收

- 压测：峰值 2 倍流量 + 2 小时长稳 + 故障注入（依赖超时、实例挂掉、缓存全失效）。
- 看 P99/P999 和超时率，不看均值。
- 灰度期间新旧版本 P99 对比，逐服务签收。
- 上线后盯一周真实 RUM，别只信压测环境。

## 五、落地节奏

- 第 1–2 周：分档、口径、基线、定位 top 瓶颈。
- 第 3–6 周：A 档服务先达标，通常 20% 的改动拿到 80% 收益。
- 第 7–12 周：B 档服务、依赖治理、把门禁和看板固化成流程。
- C 档明确不追 100ms，改为吞吐和完成时间指标。

## 六、跟老板怎么谈

一句话版本：**"可以按 100ms 交付，但按用户可感知的端到端 P99 来定义，分三档——A 档全量 100ms，B 档 300ms 量级，C 档不适用；跨地域强一致和报表类需要单独决策。预计 X 人月，先给 A 档清单和排期。"**

最好带一张表：服务、当前 P99、目标 P99、差距、改造项、预估人天、风险。让老板在"范围"和"成本"之间做选择，而不是接一个没法验收的"所有"。
