# 结论

范围从"所有服务"收敛到 4 个面向用户的接口，这事性质就变了：不再是组织级的指标运动，而是一个边界清楚、能排期的工程任务。但 180–400ms 到 100ms 这 80–300ms 的差距不是同一种难度：

- **180–250ms 的接口，大概率是优化题**：慢查询、缓存未命中、N+1、响应体过大、连接池排队。这类通常 4–6 周能压到 100ms 上下。
- **300–400ms 的接口，大概率是结构题**：慢在串行深度、跨 AZ/跨地域调用、同步外部依赖，或者干脆在请求路径里干了本该离线干的事。这类靠调优到不了 100ms，得把重活挪出请求路径，或者承认物理下限、单独定目标。

所以建议是：**4 个都接，但分两批签收，第一周只交"拆解 + 可达性判断"，不写工期承诺。** 谁在第 6 周才发现某个接口到不了 100ms，谁就被动。

另外补一句：前面提的"粒度不对"和"扇出放大"这两个坑，在你这个范围里基本消掉了——4 个接口逐个定，聚合问题不存在。剩下两条必须现在钉死：**计时口径**和**物理下限**。

## 一、先把口径钉死（半天的事，别省）

1. **计时起止点。** 建议 SLO 定义在"网关收到请求 → 写出最后一个字节"，包含应用处理、DB/缓存/RPC、序列化。客户端 RUM 单独立指标（TTFB、可交互时间），不要和服务端 P99 揉成一个数。原因很实在：手机网络单程 RTT 30–80ms 很常见，弱网下客户端可感知 100ms 几乎不可能。如果老板嘴里的 100ms 是客户端口径，先让他知道这条物理下限，否则你接的是个假目标。
2. **统计窗口。** SLO 用 1 小时滚动窗口（外加 7 天趋势），告警用 5 分钟错误预算燃烧率。别拿分钟级瞬时 P99 报警，会天天误报、最后没人看。
3. **高峰还是全天。** 写"高峰时段"，并定义高峰（比如日请求量前 20% 的小时）。全天口径会把凌晨的低负载平均进去，数字好看但没意义。
4. **错误和超时算不算。** 必须算。超时请求如果不计入 P99，就等于允许"把慢请求变成错误"来达标，这是最常见的作弊路径，下面单独说。
5. **样本量门槛。** 每接口每小时请求数低于阈值（比如 1000）时 P99 不可信，改看 P95 或直接标"数据不足"。4 个接口里如果有低流量的，提前讲清楚。
6. **4 条独立 SLO，不做聚合。** 聚合 P99 会把 400ms 那个接口藏起来，也会让两个好的替一个差的背锅。

## 二、100ms 的预算装得下什么

按服务端 85ms + 网络/客户端 15ms 粗分：

| 环节 | 预算 |
| --- | --- |
| 客户端到接入（同城、连接复用） | 10–15ms |
| 网关/鉴权/路由 | 5–10ms |
| 应用逻辑 + 序列化 | 15–20ms |
| 缓存读（本地 + Redis） | 2–5ms |
| DB 主查询（必须走索引） | 20–30ms |
| 同步下游 RPC（若必须） | 每跳 10–15ms，最多 2 跳 |
| 抖动余量 | 10ms |

这几条直接划定了改造范围：

- **同步调用深度（含 DB）≤ 3 跳。** 现在如果一次请求串 5 次 DB 再串 1 次外部 API，光串行就超预算，调优无解，只能合并、并行、缓存或移出请求路径。
- **单次 DB 查询 P99 ≤ 30ms。** 做不到就先修 DB，别在应用层浪费时间。
- **外部第三方不进主链路。** 要么本地缓存兜底，要么异步补，要么超时走降级值。
- **响应体受控**（比如原始 ≤100KB、压缩后 ≤30KB）。大 JSON 的序列化加传输经常就是 50ms 级。
- **请求内禁止无预算重试。** 重试一次等于把该请求耗时翻倍，还放大下游压力。
- **缓存命中率要 >99%。** 这不是口号，是 P99 目标的数学后果：任何占比 ≥1% 的慢路径，直接就是你的 P99。1% 未命中、1% 冷启动、1% 跨 AZ、1% 慢查询，都会把 P99 钉死在慢路径的耗时上。

最后这条是全文最关键的一句：**P99 优化不是把平均做快，是让"最慢那 1% 的成因"消失。** 所以第一步不该是改代码，而是给那 1% 的请求做成因归类。

## 三、第一周：只拆解，不优化

对每个接口做四步：

1. **采样。** 从 trace 里取 P99 以上的请求 200 条，覆盖高峰和低谷两个时段。
2. **切段。** 接入/网关、应用 CPU、GC 停顿、序列化、缓存、DB（按语句拆）、下游 RPC（按目标拆）、排队等待（线程池/连接池/限流）、重试。
3. **归因。** 按"超出预算的毫秒数 × 出现占比"排序取 top3；同时给慢请求打特征标签：缓存未命中、跨 AZ、冷启动、慢查询、串行深度 >3、重试、大响应体、锁等待、批任务时段。
4. **判可消除性。** 分三类：能消除（索引、缓存、合并）、能规避（异步、预计算、同 AZ 路由）、物理下限（跨地域、第三方长尾）。**只有前两类进 100ms 承诺**；第三类要么批预算改架构，要么改目标。

产出就一页表，每个接口一行：

| 接口 | 当前 P99 | top 成因 | 可消除性 | 主攻手段 | 预计可达 | 工期 | 风险 |
| --- | --- | --- | --- | --- | --- | --- | --- |

这张表比任何排期都有用，它是后面所有承诺的依据。

## 四、按瓶颈类型对号入座

| 瓶颈类型 | 典型特征 | 主攻手段 | 预期效果 |
| --- | --- | --- | --- |
| 慢查询/未走索引 | DB 段占一半以上，慢请求 SQL 各不相同 | 加索引、改 SQL、去 `SELECT *`、游标分页、结果缓存 | 通常砍 50–70% |
| N+1 / 串行 RPC | 调用次数随数据量增长 | 批量 IN、请求合并、无依赖并行 | 砍 40–60%，深度降下来后稳定 |
| 缓存击穿/未命中 | 慢请求集中在 TTL 到期瞬间 | 单飞重建、逻辑过期、预热、TTL 抖动 | 能消掉 80% 以上的尖刺 |
| 跨 AZ / 跨地域同步调用 | 固定多出 30–200ms，与负载无关 | 同 AZ 路由、本地副本、异步化 | 物理下限，只能规避不能优化 |
| GC / CPU / 序列化 | 应用段抖动，与流量相关 | 换低延迟收集器、减少分配、字段裁剪 | 砍 20–40% |
| 排队 / 过载 | 只在高峰出现，池和队列水位高 | 扩容、限流、池按 Little's law 校准、留 headroom | 高峰 P99 由容量决定 |
| 冷启动 / 扩容抖动 | 新实例第一批请求慢 | 预热、常驻、依赖预取 | 消掉尖刺 |
| 大响应体 | 传输和序列化占比高 | 裁剪、压缩、分页、流式 | 砍 20–50% |

4 个接口大概率共享同一批依赖（同一个库、同一批下游、同一套缓存），所以**第 2–5 周先修共享瓶颈**，一次改动 4 个接口同时受益，比逐个接口从头改划算得多。

## 五、尾部优化的动作清单（按性价比排）

1. **缓存**：单飞/互斥重建防击穿、逻辑过期、TTL 抖动防雪崩、空值缓存、热点 key 本地缓存、上线预热。目标把命中率从 95% 推到 99.5%+。
2. **DB**：慢查询 top20 逐个改；把 N 次查询合成一次批量 IN；读写分离；连接池按 Little's law 估算再压测校准，别用框架默认值。
3. **串行改并行**：无依赖的 RPC/查询并行发；把"必须串行"的链路画出来，看哪一跳能挪走。
4. **预计算**：能在写时或离线算的，不要读时算。首页、详情聚合、榜单类尤其吃这个。
5. **移出请求路径**：通知、审计、积分、搜索索引、推荐日志改消息队列，配幂等键防重。
6. **序列化与响应体**：字段裁剪、懒加载、压缩、分页。
7. **连接层**：keep-alive、连接池预热、HTTP/2 或 gRPC、TLS 1.3 + session resumption。别让请求等 TCP/TLS 握手。
8. **运行时**：低延迟 GC、控制分配速率、减少大对象。GC 停顿是典型长尾来源，几十一百毫秒一跳就进 P99。
9. **过载保护**：限流 + 排队 + 降级，用丢弃保 P99，不靠硬扛；容量留 headroom，利用率过 70% 左右延迟就非线性上升。
10. **冷启动**：预热、常驻实例、依赖预取，扩容别等打满才扩。

## 六、四个必须避开的坑

1. **拿超时当优化。** 把 timeout 从 500ms 调到 100ms，P99 数字立刻好看，但慢请求变成了错误请求。错误率不进 SLO 就等于骗指标，进了 SLO 就一点没解决。改超时本身没错，但要同时配降级、重试预算、幂等，而且 SLO 里错误率必须一起看。
2. **只盯均值。** 均值降一半、P99 纹丝不动是常态，尾部由那些占比很小的慢路径决定。
3. **批处理"不算"≠"不影响"。** 内部批处理可以不进 SLO，但它和这 4 个接口共享数据库、磁盘、CPU 时，会直接把 P99 抬起来，而且往往集中在白天跑报表的时段。要么错峰，要么独立副本/只读库，要么资源限额。否则"不算"只是纸面豁免。
4. **用缓存掩盖一致性问题。** 缓存能把 400ms 变 20ms，但失效、脏读、多副本一致性策略要写清楚，不然延迟达标、数据出错。

## 七、验收

- **逐接口签收**：高峰 1 小时窗口 P99 ≤ 100ms，同时错误率、超时率不劣化。再看两个补充指标：P99.9，以及"超过 100ms 的绝对请求数"——P99 达标时仍有 1% 的慢请求，这个绝对量业务得能接受。
- **压测**：峰值 2 倍流量 + 2 小时长稳 + 故障注入（依赖超时、实例摘除、**缓存全失效**）。最后这个必须演练，缓存一失效 P99 会瞬间回到原来的 400ms。
- **灰度**：新旧版本同窗口对比，逐接口签收，劣化超 10% 自动回滚。
- **上线后**看一周真实 RUM 和 trace，别只信压测环境。

## 八、节奏和人力

- 第 1 周：口径 + 拆解 + 4 份可达性判断。这是第一个交付物，比代码重要。
- 第 2–5 周：共享瓶颈（DB、缓存、连接池、序列化、依赖 deadline）。这段通常拿走一半以上的差距。
- 第 6–9 周：单接口结构改造（预计算、并行化、异步化、流式返回）。
- 第 10–12 周：压测、灰度签收、门禁固化成流程。
- 人力估算：2 名后端 + 0.5 名 DBA + 0.5 名 SRE，8–10 周。若有两个接口需要结构改造，按 12 周排。

如果这 4 个里有页面聚合接口（一次请求扇出十几个下游），100ms 不能靠"每个下游都快"来凑：按并联概率算，每个下游都有 99% 达标，15 个并联仍有约 1−0.99¹⁵ ≈ 14% 的概率至少一个慢。正确做法是把首屏关键内容收敛到 1 条主链路（≤100ms），其余用流式/分段返回或异步补齐，前端先渲染。这条往往比后端调优更有效。

## 九、怎么对上说

一句话：**"4 个接口都接。100ms 按服务端口径、高峰期 1 小时窗口、错误和超时计入。180–250ms 的两个，4–6 周可到；300–400ms 的两个，第一周给拆解和可达性判断，如果慢在串行深度或跨地域，需要把重活移出请求路径，工期 10–12 周，或者那个接口单独定 150ms。"**

带那张"接口 / 当前 P99 / top 成因 / 可达值 / 工期 / 待决策项"的表去谈，让选择落在"改架构、调目标、加人"三者上，而不是落回"能不能做到"。

需要现在拍板两件事：

1. **计时口径**：服务端还是客户端、高峰怎么定义、错误是否计入。不定这个，可达性判断没有意义。
2. **物理下限的处理方式**：如果拆解显示某个接口的极限在 130–150ms，是批预算改架构，还是把该接口目标改成 150ms。

最后，把"4 个接口要 100ms、内部批处理不在范围内"写成 SLO 文档，列明接口名和排除清单。不写下来，三个月后大概率又变回"所有服务都要快"。
