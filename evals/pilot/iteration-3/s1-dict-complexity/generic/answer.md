# 结论

平均 **O(1)**，最坏 **O(n)**。`dict` 和 `set` 底层是同一套哈希表实现（`set` 可以看作只有键、没有值的 `dict`），所以查找（`d[k]`、`k in s`）的复杂度结论一致。

# 为什么平均是 O(1)

- 查找时先算出 key 的哈希值，用 `hash & mask` 直接算出索引表里的槽位，不需要随元素个数线性扫描。
- 哈希分布均匀时槽位很少冲突；CPython 把负载因子压在 2/3 以下，超过就扩容重排，因此期望探测次数是常数，通常一两次就能命中或确认键不存在。
- CPython 3.6 起 `dict` 是"紧凑"布局：一张稀疏索引表存槽位下标，一张按插入顺序排列的 entries 数组存 hash/key/value。查找只查索引表，遍历只走 entries，二者互不拖累。

# 为什么最坏是 O(n)

- 采用开放寻址加伪随机探测：如果大量 key 落到同一批槽位（哈希函数差，或被人为构造），每次查找都得沿探测序列走完整个表，退化成 O(n)。
- 3.3 起 `str`/`bytes` 的哈希带进程级随机种子（SipHash），正是为了防这种构造碰撞攻击，攻击者无法预先造出大量同槽键。
- 还有一个常被忽略的成本：相等比较本身未必是 O(1)。字符串比较最坏是 O(长度)，所以严格讲一次查找是"哈希 O(1) + 若干次相等比较"，长键上常数明显更大。

# 实践含义

- "平均 O(1)"不等于"永远快"：哈希计算、常数因子、缓存局部性都在。数据量很小时，list 的线性扫描有时反而更快。
- 需要有序操作（取最小/最大、范围查询、按序遍历）时 `dict`/`set` 帮不上忙，要用 `sortedcontainers` 或先排序。
- 自定义对象当键时，`__hash__` 与 `__eq__` 必须一致，哈希只能基于不可变字段；用可变对象做键会破坏哈希表结构。
