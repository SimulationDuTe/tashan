## 结论：先别查数据库，问题大概率在上周加的推荐链路上

最可能：个性化推荐把「读用户画像」同步挂进了订单查询的关键路径。10:00–11:00 这个固定窗口里，它依赖的共享资源变慢——最可能是画像库或缓存被同一时段的离线画像任务争用，或者某个连接池被打满——一部分请求排队到撞上 5s 超时。P99 正好卡在 5s 这种整数上，更像代码或网关配的超时，而不是真实处理耗时，真实耗时不会这么整齐。

**现有证据为什么指向这里**

- 只有 P99 涨、均值多半没怎么动：少数请求被卡住，符合排队和锁等待，不符合 CPU 打满。
- CPU、内存、连接数正常：等 I/O、等排队本来就不烧 CPU；「连接数正常」常常只是池子长期开满，看不出正在等。
- DB 慢查询日志干净：它只统计 SQL 执行时间，不算取连接的等待、应用内锁、远程调用和网络。时间很可能花在 SQL 之前。
- 10–11 点固定出现：要么是流量峰值，要么是同时间有离线任务在读同一份画像。一条曲线就能把这两种分开。

有两种具体机制值得优先验证，都能解释「慢查询日志干净、只有 P99 坏」：

1. 单次订单请求里逐条查画像，一页 50 单就是 50 次串行调用，每次几十到一百毫秒，叠起来正好到秒级；
2. 画像缓存同一时刻集体失效或池子被占满，请求卡在取连接处排队，SQL 根本没发出去。

**需要你确认两点**：那个 5s 是代码或网关里配的超时吗？10 点是不是整点开始、11 点整点结束？

## 先做判定，再动手（约半小时）

1. 把 09:00–12:00 的 P99 按分钟画出来，叠加订单 QPS：10:00 陡起而 QPS 平，是定时任务；随 QPS 爬升，是容量或争用。
2. 抽 3 条慢请求看链路瀑布：5s 花在画像/推荐调用、连接池等待，还是 SQL。这一步基本能定案。
3. 数一下单次订单请求里画像调用的次数，同时看画像服务或缓存在该时段的 P99、池 active/wait、线程池队列长度。

## 改法

当天可做、可回滚：把推荐从订单查询的同步链路摘出去。给画像调用 50–100ms 预算，超时或异常就直接返回订单、推荐留空；用独立线程池隔离，禁止自动重试。订单接口的 P99 应该立刻回到 300ms 量级。推荐短暂降级，比订单查询 5s 划算得多。

再按判定结果修根因：

- 离线任务争用：在线读走只读副本或独立缓存命名空间，任务错峰或读快照，不与在线共用实例和热点 key。
- 池子或缓存被打穿：按并发量算池大小，画像加本地缓存、TTL 抖动和单飞，防同一时刻集体失效。
- 调用次数太多：批量取画像，或离线算好推荐放 KV，在线只读一次。

不要先加机器或扩 DB——CPU 正常说明不是算力问题，加了也白加。

## 怎么算修好

10:00–11:00 的 P99 稳定低于 400ms，连续三天；同时看 P99.9 和最大值有没有残留长尾、推荐降级率、订单数据正确性。降级率超过事先约定的比例，就回滚开关。
