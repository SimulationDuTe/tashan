## 结论

订单查询本身没有变慢，是它上周新增的**同步画像读取**在 10–11 点被拥塞卡住：这个时段并发最高，把某个**有界资源**（连接池、线程池或一把锁）推过了排队阈值，订单请求就从「算 300ms」变成「等 5s」。

真正要决定的是一件事：**画像读取算不算订单查询的必需依赖**。现在的接法把它当成必需依赖，于是画像侧的任何拥塞都等比放大成订单接口的长尾。而它只是锦上添花的数据，本该是可降级的。

CPU、内存、连接数、慢查询日志全都「正常」，恰恰是「在等、不在算」的典型指纹——其中「连接数正常」最容易被误读。

## 把「正常」的指标反过来读

- **CPU、内存正常** → 请求时间不花在计算上。5s 里有 4.7s 是阻塞等待，CPU 当然不高。
- **DB 慢查询日志干净** → 慢的不是 SQL 执行，是拿到连接前后的等待。单条 SQL 仍是 5ms，日志一笔不记。
- **连接数正常** → 池是固定上限，打满后连接数恒定停在 max，曲线看起来最「稳定」。该看的是**借连接的平均等待时间与等待队列长度**，不是连接数量。
- **只在 10–11 点** → 这不是线性劣化，是**跨过了拥塞阈值**：并发需求 = QPS × 单次持有时间，平时 ρ<1 怎么加量都不明显，峰值 ρ>1 后队列无上限增长，直到撞超时。这解释了为什么边界这么锋利、其他时段完全正常。
- **5s 是个整数** → 大概率是某个 timeout 的截断值（HTTP 客户端、Feign、网关），而且外面套了 try-catch 返回空推荐，所以错误率没涨、只有延迟涨。

## 最可能的机制（按概率）

1. **在事务或已借出的连接里发远程调用**。最隐蔽也最常见：画像调用写在 `@Transactional` 内，或写在借出连接之后，连接持有时间从 ~5ms 涨到 200–300ms，池的需求量放大几十倍。峰值池打满 → 排队 → P99 撞 5s。这一条能同时解释上面四个「正常」。
2. **逐条调用放大（N+1）**。一个订单 N 个商品或权益，循环里各查一次画像，串行累加；长订单才会进 P99，中位数看不出问题。
3. **本地缓存的全局锁或单飞失效**。画像缓存用一把大锁刷新，高峰期锁护航，线程全部 BLOCKED。
4. **画像侧自己在 10 点有批量任务或缓存集中过期**，拥塞源在上游。这条与 1–3 不互斥，通常是「触发源 + 耦合方式」的关系。

## 一次抓取就能定死

10:30 前后连抓 3 次 `jstack`，只看订单接口线程停在哪个栈：

- `BLOCKED (on object monitor)` → 机制 3，锁。
- `WAITING` 在 `getConnection` / `borrowObject` → 机制 1，连接池。
- `TIMED_WAITING` 在 `socketRead0` 且栈中含画像服务 → 机制 2 或 4，下游慢。

同时对比 10:30 与 15:00 的画像调用 P99 和池等待时间；再看 P99.9 是否被截在 5s 上方——断崖式截止说明是超时，继续往上爬说明是排队。

顺手确认两个会改变结论的事实：画像调用是否与订单查询共用同一个连接池或线程池；10 点是否有对账、报表或画像 ETL 定时任务。共用则优先做隔离；有定时任务则那是触发源，需要错峰或预热。

## 改法

**今天止血：把必需依赖改回可选依赖**

- 画像调用超时压到 50–100ms（远小于接口预算），失败立即返回空推荐，不重试。
- 加熔断：连续失败 N 次直接跳过画像调用，10 分钟后半开。
- 先用开关关掉画像调用，跑一个 10–11 点窗口，确认 P99 回到 300ms 再动结构。

**本周结构：消除耦合**

- 事务外调用：先取订单、提交事务、归还连接，再取画像；或干脆不共用连接池。
- 独立线程池或信号量做舱壁，画像调用打满也不许占订单查询的线程。
- 批量取：用一次 mget 或批量接口取一页订单所需的全部画像，禁止循环内 RPC。
- 能异步就异步：订单先返回，推荐位由前端二次拉取或服务端预取填充。
- 池容量按 `峰值 QPS × 单次持有时间 × 1.5` 重算，并先核对画像调用真实的持有时间。

**10 点窗口**

- 核对画像侧的批量任务与缓存 TTL 是否都压在 10–11 点。错峰、提前预热，或对热点用户画像加长 TTL 并后台刷新。

## 怎么验证

- 因果确认：关掉画像调用，同一时段 P99 回到 300ms。
- 改完看四个数：接口 P99、画像调用 P99、借连接等待时间、降级或熔断触发次数。P99 回到 300ms 附近，且峰值时降级次数不为 0（说明兜底真的在拦），才算改对。
- **会推翻本判断的观察**：关掉画像调用后 P99 仍是 5s。那说明 10 点窗口另有触发源（备份、对账、统计跑在同一库或同一缓存），应转去查定时任务，不要在画像上继续加码。
