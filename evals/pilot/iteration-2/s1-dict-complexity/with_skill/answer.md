平均 O(1)，最坏 O(n)。

原因很简单：dict 和 set 底层都是哈希表，set 基本就是一个只有键、没有值的 dict。查找时先对 key 算 hash，再用它对表的槽位数取余，直接定位到某个槽位去看看——槽是空的，就说明不存在；槽上的 key 相等，就是找到了。这一步的开销和里面装了多少元素无关，所以是常数时间。

"平均"两个字靠两件事撑住：

- **表比元素稀疏。** 元素一多，哈希表就扩容，负载因子（已用槽位 / 总槽位）大致压在 2/3 附近。槽位空得多，随便一个 hash 撞上别人位置的几率就低，探查一两次就能结束。
- **hash 足够散。** 字符串用的是加了随机种子的哈希，同一份数据在不同进程里算出来的值不一样，避免别人构造大量同槽的 key 来打垮服务。

但 O(1) 是平均，不是保证。如果一堆 key 恰好落在同一个槽（自定义 `__hash__` 写坏了，或者刻意构造的冲突），冲突探查会退化成线性扫描，单次查找就是 O(n)。另外严格讲，算 hash 本身有成本：字符串的哈希是 O(len)，只不过算完会记在对象上，重复查找不再重算。

所以结论是：正常使用下，查找和插入都可以按 O(1) 估算；只有在哈希分布被破坏时，才需要警惕退化到 O(n)。
