# dict 和 set 的查找复杂度

**结论：平均 O(1)，最坏 O(n)。**

`dict` 的按键查找、`set` 的成员判断（`in`）都是哈希表操作，平均情况下与元素个数无关，所以是常数时间；但在哈希冲突严重、大量键落到同一个桶时，会退化成扫描链表/探测序列，最坏到 O(n)。

## 为什么是 O(1)

两者底层都是哈希表：先用 `hash(key)` 算出哈希值，再对表长取模（实际是 `mask = size - 1` 后按位与，因为容量取 2 的幂）得到桶下标，然后直接跳到那个桶去比对。

```
index = hash(key) & (table_size - 1)
```

少了"逐个比较"这一步，查找就不需要遍历整个容器，平均只做常数次比较，所以是 O(1)。

几个关键实现细节（CPython）：

- **开放寻址**，不是链地址法。冲突时不挂链表，而是按固定的探测序列找下一个空位/目标位。CPython 用的是一种改进的伪随机探测：`perturb = hash; i = hash & mask;` 每次 `i = (i * 5 + perturb + 1) & mask; perturb >>= 5`，能让高位也参与探测，缓解聚集。
- **每个 entry 存了哈希值**。比对时先比哈希（整数比较，很快），哈希相同才调用 `==`，所以即使有冲突，也不会对每个键都做昂贵的 `__eq__`。
- **负载因子控制在 2/3**。`dict`/`set` 的已用槽位超过容量的约 2/3 就扩容（容量翻倍并重新散列），保证平均探测长度很短。这是"平均 O(1)"工程上成立的实际原因。
- **3.6+ 的紧凑 dict**：`dict` 拆成"稀疏的索引数组 + 密集的 entries 数组"，索引数组只存下标，entries 按插入顺序排列。省内存、遍历更快，复杂度结论不变；`set` 仍是纯哈希表，没有这层拆分。

## 什么时候不是 O(1)

复杂度是**平均**值，前提是哈希函数把键均匀分散。以下情况会恶化：

- **哈希冲突被人为制造**：所有键哈希到同一桶（例如自定义 `__hash__` 返回常量），探测序列退化为线性扫描，最坏 O(n)。
- **哈希函数本身很慢**：比如对超长字符串先算哈希，单次 `hash()` 是 O(长度)，这部分成本独立于元素个数，但会让单次操作变贵。
- **频繁扩容**：插入触发的 rehash 是 O(n)，不过它是摊还的，均摊到每次插入仍是 O(1)。
- **键不可哈希**：`list`、`dict` 之类不能作为键，直接 `TypeError`，谈不上复杂度。

## 顺带一提

- 查找依赖 `__hash__` 和 `__eq__` 一致：两个相等对象必须有相同哈希，否则查不到。
- 遍历 `dict`/`set` 的顺序是哈希表内部顺序（`dict` 3.7+ 保证插入顺序），这与查找复杂度无关。
- `list` 的 `x in list` 是 O(n)、按索引取值是 O(1)；需要判断"在不在"且元素可哈希时，优先用 `set`。
