# 结论

问题不在数据库，也不在机器资源，而在订单查询链路里新加的「读用户画像」这个**同步调用**：它把推荐系统的尾部延迟直接传染给了订单查询。10:00–11:00 是触发窗口——业务峰值把线程池利用率推到非线性区，或者 10 点整有定时任务/缓存集中失效——此时画像读取变慢，而订单查询与它共用线程池、没有隔离也舍不得快速失败，少量慢请求就占住工作线程，队列一堆积，P99 直接顶到 5s 的超时上限。

三个现象正好互相印证：

- **P99 恰好是 5s** 这种整数，通常不是"变慢"，而是某个 `timeout` 配置值。意味着 P99 反映的是"超时请求占比 ≥ 1%"，而不是所有请求均匀慢了 16 倍。
- **CPU、内存、连接数正常，DB 慢查询干净**：时间不花在计算上，也不花在 SQL 执行上，而是花在"等"上——等下游返回、等线程、等锁。慢查询日志只记 SQL 执行时间，记不到连接池等待和网络往返。
- **只在 10–11 点**：要么流量峰值让排队进入非线性区，要么 10:00 有定时任务或缓存批量失效。

# 先用半小时确认（按顺序做，第一条能一锤定音）

1. **抓 trace**：筛出 P99 > 3s 的订单请求，看时间花在哪个 span。如果大部分卡在 profile / recommend 的 RPC 上，基本实锤。
2. **找 5000ms**：在代码和配置里搜超时设置。P99 = 5s 几乎就是这个值；顺便确认有没有 `retry=2/3`——重试会把一次慢放大成三次。
3. **看 10:00 前后两个数**：画像缓存命中率、画像服务 QPS 与超时数。命中率骤降 + QPS 尖峰 = 缓存集中失效；命中率不变而线程池队列暴涨 = 排队放大。
4. **看线程池而不是连接数**：active 线程数、队列长度、拒绝数，以及连接池 `acquire` 等待时间。连接数"正常"只说明没泄漏，说明不了没排队。

# 最可能的两个原因

**A. 峰值下的排队放大（更常见）**
新增的同步调用没有独立资源池，和订单查询抢同一个 Web 线程池。10 点订单 QPS 到峰值，原本 300ms 的请求已把池子用到 70% 左右；再叠加画像在缓存 miss 时的 1–3s 尾巴，按 ρ/(1-ρ) 的排队曲线，利用率从 70% 到 90% 延迟就翻几倍。CPU 看起来正常，因为线程都在 wait，不在算。

**B. 10:00 定时任务 / 缓存集中失效**
画像每天 10 点重算、缓存 TTL 恰好对齐同一时刻、或运营 10 点推送导致大量用户同时活跃。瞬间 miss 率飙升 → 画像服务被打穿 → 全部超时。特征是 P99 在 10:00–10:10 最严重，随后随缓存回填逐步缓解；P99 曲线与流量曲线不同步。

两者的区分很简单：把 10 点的 P99 曲线和 QPS 曲线叠在一起，同步上涨是 A，P99 尖峰但 QPS 平稳是 B。

# 改法

## 今天就能止血

1. **缩短超时**：订单查询总预算 500ms，画像最多给 50ms。5s 这种设置等于没有超时——一次卡死会拖垮整批请求。
2. **熔断降级**：超时率或错误率过阈值就自动摘掉画像读，返回默认排序/无个性化结果。订单查询的可用性不能被推荐绑架。
3. **资源隔离**：画像调用走独立线程池（有界队列 + 满了直接降级），或用信号量限流，禁止和订单查询共用。
4. **改成异步或并行**：推荐位让前端二次请求，或后端 `CompletableFuture` 并行取、总 deadline 到了就先返回订单主体，别串行等。
5. **砍重试**：最多重试 1 次，且必须在总预算内，别让重试把 50ms 变成 150ms。

## 本周根治

6. **缓存三件套**：本地 Caffeine（5–10 分钟）+ Redis；TTL 加随机抖动，避免同一秒集体过期；逻辑过期（值里带 expireAt，过期后异步刷新，先返回旧值）防击穿；每个 key 用 single-flight 只放一个请求回源；空结果也缓存，防穿透。
7. **双缓冲**：批量重算画像时写新版本 key，写完原子切换指针，读方永远读到完整版本，不会在重建窗口里读到空或慢。
8. **错峰 + 分批**：10 点的重算挪到凌晨，或按用户分片滚动更新，每批 1%–5%。
9. **预计算**：把「读画像 + 算推荐」离线做好，在线只做一次 Redis GET。在线链路不该有实时计算。
10. **容量与压测**：画像服务按时段扩缩容；用 10 点的真实流量做一次全链路压测，验证 500ms 预算是否成立。

## 观测补齐

- 每个外部依赖单独看 P99 和超时率，不要只看接口总 P99。
- 订单接口的 SLO 分「含降级」和「不含降级」两个口径统计，否则降级成功会把问题掩盖掉。
- 线程池 active / queue / reject、连接池 acquire 等待时间，都进看板。
- 加一条告警规则：**P99 逼近某个超时配置值时，按"超时型劣化"告警**，而不是等它变成 5s。

# 验收标准

灰度 10% 流量，在 10–11 点对比：订单 P99 回到 400ms 以内、画像超时率低于 0.5%、线程池队列峰值不随时间上涨、降级触发率可控。达标后再全量。
