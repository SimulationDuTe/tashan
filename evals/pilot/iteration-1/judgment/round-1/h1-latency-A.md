# 结论

问题不在数据库，也不在机器容量——**订单查询在 10:00–11:00 是在排队等，不是在干活**。

最可能的情况是：上周上线的个性化推荐（读用户画像）和订单查询**共用了同一段链路或有界资源**（一次同步的画像调用、同一个线程池、同一个连接池、同一个画像存储），而画像/推荐侧每天 10 点有一次**批量刷新或缓存统一过期**。这段时间订单请求被挂住，一直等到超时（5s，大概率就是你某个配置里的超时值）才返回。

CPU、内存、连接数、慢查询日志这四个「正常」，恰好都是**看不见排队**的指标——所以我建议先把它们放到一边，直接去量「等待」。

# 为什么这四个「正常」一个都不能排除问题

| 指标 | 它实际能证明什么 |
| --- | --- |
| CPU 正常 | 说明请求没在算。而「在等」本来就不烧 CPU。**低 CPU + 高延迟 = 排队/阻塞的典型特征**，不是健康信号。 |
| 内存正常 | 不排除一次批量加载把堆推高再回落，也不排除 GC。单看瞬时内存曲线很容易漏。 |
| 连接数正常 | 如果连接池是固定大小（比如 max=20），**打满时读数反而是平的**。要看的不是连接数，是连接池的等待时间/等待请求数。 |
| DB 慢查询无异常 | 慢查询日志只记「执行超过阈值」的 SQL。请求**在应用侧等连接**根本没到 DB；等行锁的 SQL 执行本身很快，也不会记为慢。 |

关键认知：**延迟 = 执行时间 + 等待时间**。上面四个指标全在量「执行」，没有一个在量「等待」。所以症状全都指向等待，指标却全都正常。

# 从 300ms 到 5s，发生了什么

吞吐没掉、延迟涨 16 倍，按 Little's Law（在途请求数 = 吞吐 × 延迟），在途并发也涨了约 16 倍。这些请求不可能都在计算——它们被 **park 在某个有固定容量的地方**：线程池、连接池、锁、Redis 单线程、下游配额。

而「每天固定 10–11 点」是一个强信号：**触发源一定有定时属性**，不是随机负载波动。三个特征叠起来——固定时刻出现、只在尾部分位、不耗资源——指向同一个机制：一个每天 10 点开始的定时动作，占住了订单链路依赖的某个共享资源。

另外，P99 独涨（如果 P50 基本没动）是排队问题的典型指纹：利用率逼近 1 时，队列长度的尾部分布急剧拉长，均值只涨一点，P99 涨十倍。这也解释了为什么你们看「平均响应时间」可能没觉得多严重。

# 最可能的三种具体形态（按概率）

1. **订单接口里新增了一次同步的画像/推荐调用**（订单页要显示「猜你喜欢」）。画像服务 10 点做批量刷新或大表重建，RPC 变慢；5s 很可能就是那次调用的超时，或者「超时 + 重试」叠出来的整数。
   特征：APM 里订单接口的子 span 中，有一条画像 RPC 占了大头。

2. **画像缓存统一过期（缓存雪崩）**。夜间预计算写入缓存，TTL 设成固定值（例如 12 小时），10 点前后集中失效，请求同时回源，把共享池和画像库瞬间打满。
   特征：缓存命中率在 10:00 断崖下跌，回源 QPS 出现尖峰。

3. **推荐和订单共用一个线程池/连接池**，10 点的推荐批处理占满池子，订单请求只能排在后面。
   特征：池的活跃数和等待队列在 10 点顶到上限，但「连接数」读数看起来没变化。

三种形态根因是同一件事：**没有隔离，且存在一个同步的固定时刻**。所以下面的止血和根治对三种都适用。

# 今晚就能做的止血（按性价比排序）

1. **先加开关**：给推荐/画像调用加一个 feature flag，一键关掉，订单接口立刻恢复。先有兜底手段，比什么都重要。
2. **超时 + 熔断 + 降级**：画像调用超时设 50–100ms（不是 3s/5s），连续失败直接熔断，失败时返回空推荐。**订单主流程绝不能因为推荐失败而变慢或报错。**
3. **物理隔离**：给画像/推荐单独的线程池和连接池（舱壁模式）。池满只影响推荐，不抢订单的线程。
4. **挪出主链路**：推荐改成异步（订单先返回，推荐后到），或由前端并行请求，不要串行塞在订单接口里。
5. **缓存防雪崩**：TTL 加 ±10% 随机抖动；热 key 用 singleflight 只放一个请求回源；更好的做法是逻辑过期 + 后台线程提前刷新，永远不让请求等回源。

# 30 分钟内怎么确认是哪一种

按这个顺序走，每一步都能砍掉一批假设：

1. **拆分位数**：拉 10–11 点的 P50/P90/P99 和 QPS。P50 也涨到秒级 → 整个应用被一起卡住（全局锁/GC/池），排查直接跳到抓栈；只有 P99 涨 → 就是排队，继续往下。同时看该时段 QPS 是否也涨，涨了才需要考虑「流量峰 + 推荐对冷用户命中率低」这条支线。
2. **量等待，不量执行**：用 APM 把订单接口拆成子 span，看时间到底花在 DB、Redis，还是那条画像 RPC 上；同时看线程池队列长度、Tomcat busy threads、连接池的 wait time / pending 数。这一步通常就能定案。
3. **对时间轴**：列出调度平台在 9:50–10:10 的任务（画像更新、报表、对账、券、推送）。延迟曲线的起点和某个任务的启动时间对齐，基本就锁定触发源了。
4. **查缓存 TTL**：夜间的预计算时间加上 TTL，是否正好落在 10 点。这能确认雪崩形态。
5. **抓栈/火焰图**：10:10 左右抓 30 秒（async-profiler / pprof / py-spy）。如果线程大量停在 pool acquire、lock、socket read 上，就直接证明了「在等」。
6. **反查「5s」这个数字**：它是哪个配置里的超时？RPC 超时、网关超时、池等待超时、还是「重试次数 × 单次超时」。命中哪个，就是哪条链路——这一步往往最快。

# 根治

- **订单主链路只依赖强一致、低延迟、自己完全掌控的存储**。推荐/画像是旁路能力，可以慢、可以没有。
- **按依赖做舱壁**：每个外部依赖独立的线程池、连接池、超时和熔断阈值。慢依赖不拖垮全站。
- **批任务错峰 + 限速 + 双 buffer**：画像刷新挪到凌晨低峰，或「新版本算好再原子切换」，从根上消除「统一失效」。
- **按 P99 定容，不按均值**：用 Little's Law 反推池大小（并发 = 目标 QPS × 目标 P99），而不是按平均 QPS 拍一个数。

# 怎么算改好了

验收标准不是「P99 回到 300ms」，而是**画像变慢时订单不受影响**：

- **故障注入**：人为把画像服务延迟到 3s，订单查询 P99 仍应 < 300ms（超时 + 降级生效）。
- **窗口回放**：10 点时段压测，P99 回到 300ms 量级；画像调用超时率、熔断次数有独立告警，且这些告警不会升级成订单接口的告警。

满足这两条，才算真正隔离，而不是把这次的定时炸弹拆掉、等下一次换个触发点再爆。
